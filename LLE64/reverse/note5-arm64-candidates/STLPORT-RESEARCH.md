# AArch64 STLport research for the Note 5 AOJ4 effects

Date: 2026-07-14

Scope: `libColourDropletEffect.so` and `libSparklingBubblesEffect.so` under
`reference/arm64-candidates/note5-aoj4`. This is a source/runtime provenance
investigation only. No APK, build output, native candidate, Ghidra database, or
packaged library was changed.

## Result

There is an authentic, reproducible route: build the **Android platform**
`libstlport` module from AOSP 5.1.1 for `aosp_arm64`. AOSP's Lollipop STLport
source defines all five ABI entries imported by both Samsung libraries, and the
Lollipop platform build has a first-class ARM64 product using GCC 4.9. This is
the correct family of runtime: SONAME `libstlport.so`, linked to the platform
minimal `libstdc++.so`.

An official AOSP NDK AArch64 `libstlport_shared.so` also exists and exports the
same five names. It is useful as independent proof that the source produces the
required AArch64 mangling and object layout, but it is **not an authenticated
drop-in**: its SONAME, dependencies, and C++ runtime composition differ. The NDK
documentation explicitly says its name was chosen to avoid the system
`libstlport.so`, whose ABI was not stable and could not be mixed with
NDK-generated code. Renaming the NDK binary is therefore not the recommended
solution.

Confidence:

- AOSP 5.1.1 source supports/builds ARM64 `libstlport.so`: **HIGH**.
- Required five symbols are produced with the exact AArch64 names: **CONFIRMED**
  by source plus an official AOSP AArch64 prebuilt.
- A clean AOSP 5.1.1 platform build is compatible with Samsung's AOJ4 blobs:
  **MEDIUM-HIGH**, pending loader and smoke testing on the target. Samsung may
  have carried private patches, although the local Samsung ARM32 runtimes have
  the same source-level ABI and platform dependency shape.
- Renamed NDK `libstlport_shared.so` is safe to ship: **LOW / NOT ESTABLISHED**.

## 1. Exhaustive local search

`rg --files -uu -g 'libstlport.so'` over `D:\New project` found eleven files:
one AArch64 probe shim already generated by LLE64 and ten historical Samsung
ARM32 files. The ten ARM32 files reduce to five distinct SHA-256 values. No
authentic ELF64/AArch64 Samsung or platform `libstlport.so` exists in the local
dumps, including untracked files.

| Kind | Count | Architecture | Notes |
|---|---:|---|---|
| LLE64 probe shim | 1 | ELF64 AArch64 | 6,320 bytes; SHA-256 `451CB8C3E034A5205D7EA00961E2E0576176D7779493BDC95391C0CBCC1B00C2`; intentionally not a real STLport runtime |
| Historical Samsung runtime | 10 | ELF32 ARM | five distinct contents; none loadable in a 64-bit process |

- `3EF8D2EB3BC6BD02ACAE01E77668864030FFF78A8737606CF06372CF564C669A`

The app-original ARM32 runtime has `DT_NEEDED` `libc.so`, `libm.so`, and
`libstdc++.so`, with SONAME `libstlport.so`. It exports the 32-bit counterparts
of the five required symbols. In particular, `size_t`/`unsigned int` is mangled
as `j` on ARM32:

- `_ZNSt12__node_alloc11_M_allocateERj`
- `_ZNSt12__node_alloc13_M_deallocateEPvj`
- `_ZNSt8ios_base16_M_throw_failureEv`
- `_ZSt24__stl_throw_length_errorPKc`
- `_ZSt4cout` (88-byte object in this build)

That dependency shape is evidence that the Samsung effects target the Android
**platform** STLport, not the NDK application runtime.

## 2. AOSP 5.1.1 contains the matching implementation

The AOSP tag [`android-5.1.1_r1`](https://android.googlesource.com/platform/external/stlport/+/refs/tags/android-5.1.1_r1)
resolves to STLport commit
[`d0388a36b67665be55162388337055ee21a43206`](https://android.googlesource.com/platform/external/stlport/+/d0388a36b67665be55162388337055ee21a43206).
Its [`Android.mk`](https://android.googlesource.com/platform/external/stlport/+/d0388a36b67665be55162388337055ee21a43206/Android.mk)
lists the complete runtime source set and builds shared module `libstlport`; it
does not contain an ARM32-only restriction.

The exact imported facilities are present:

| Samsung import | AOSP definition/evidence | AArch64 ABI consequence |
|---|---|---|
| `_ZNSt12__node_alloc11_M_allocateERm` | [`src/allocators.cpp`, `_M_allocate(size_t&)`](https://android.googlesource.com/platform/external/stlport/+/d0388a36b67665be55162388337055ee21a43206/src/allocators.cpp#742) | AArch64 `size_t` is `unsigned long`, Itanium code `m` |
| `_ZNSt12__node_alloc13_M_deallocateEPvm` | [`src/allocators.cpp`, `_M_deallocate(void*, size_t)`](https://android.googlesource.com/platform/external/stlport/+/d0388a36b67665be55162388337055ee21a43206/src/allocators.cpp#745) | `void*`, then AArch64 `size_t` (`m`) |
| `_ZNSt8ios_base16_M_throw_failureEv` | [`src/ios.cpp`](https://android.googlesource.com/platform/external/stlport/+/d0388a36b67665be55162388337055ee21a43206/src/ios.cpp#207) | ordinary exported member function |
| `_ZSt24__stl_throw_length_errorPKc` | [`stlport/stl/_range_errors.c`](https://android.googlesource.com/platform/external/stlport/+/d0388a36b67665be55162388337055ee21a43206/stlport/stl/_range_errors.c#72) | exact free-function name/signature |
| `_ZSt4cout` | [`src/iostream.cpp`](https://android.googlesource.com/platform/external/stlport/+/d0388a36b67665be55162388337055ee21a43206/src/iostream.cpp#70) and [`stlport/iostream`](https://android.googlesource.com/platform/external/stlport/+/d0388a36b67665be55162388337055ee21a43206/stlport/iostream#71) | real `std::ostream` storage and initialization, not shim bytes |

The Android configuration defines `_STLP_NO_EXCEPTIONS`; the Lollipop build
also globally uses `-fno-exceptions`. Consequently the authentic platform
helpers use the no-exception behavior (for example, range-error paths print and
abort, while the ios failure path prints). This is another reason to build the
original module rather than approximate the functions individually.

A later AOSP change is unusually direct evidence for this exact use case:
commit
[`862ba3df3cd824fbecc7e18b371d8ec0d43ed653`](https://android.googlesource.com/platform/external/stlport/+/862ba3df3cd824fbecc7e18b371d8ec0d43ed653)
states that STLport was retained only for devices depending on vendor blobs
that had not yet been fixed. This is consistent with the two Samsung AOJ4
vendor libraries.

## 3. ARM64/toolchain/API support

Android's official
[`NDK revision history`](https://developer.android.com/ndk/downloads/revision_history)
records that NDK r10 (July 2014) introduced `arm64-v8a`, with Android L/API 21
as the first 64-bit level and GCC 4.9 as the default/only GCC for 64-bit ABIs.
NDK r10e (May 2015) was current when Android 5.1.1 and the Note 5 generation
were built.

More importantly for the platform runtime, the AOSP 5.1.1 build tree contains
`aosp_arm64`/`generic_arm64`; its board configuration sets `TARGET_ARCH :=
arm64`, `TARGET_ARCH_VARIANT := armv8-a`, and `TARGET_CPU_ABI := arm64-v8a`.
[`TARGET_linux-arm64.mk`](https://android.googlesource.com/platform/build/+/android-5.1.1_r1/core/combo/TARGET_linux-arm64.mk)
selects `aarch64-linux-android-4.9` and GCC/G++ by default. The source manifest
is the official
[`android-5.1.1_r1` platform manifest](https://android.googlesource.com/platform/manifest/+/android-5.1.1_r1).

Therefore this is not a speculative modern port: the original Lollipop build
system was able to emit a platform AArch64 `libstlport.so` at API 21.

## 4. Independent confirmation from official AOSP prebuilts

The official AOSP repository `platform/prebuilts/ndk` at Android 5.1.1 commit
[`2f308b8bad568d044288b2e79fcc1a894fd58787`](https://android.googlesource.com/platform/prebuilts/ndk/+/2f308b8bad568d044288b2e79fcc1a894fd58787)
contains AArch64 STLport prebuilts. I inspected two blobs directly from that
Git commit, without copying either into LLE64:

| Official blob | SHA-256 | ELF | Required exports |
|---|---|---|---|
| [`8/.../arm64-v8a/libstlport_shared.so`](https://android.googlesource.com/platform/prebuilts/ndk/+/2f308b8bad568d044288b2e79fcc1a894fd58787/8/sources/cxx-stl/stlport/libs/arm64-v8a/libstlport_shared.so) | `1013BC255EE7EF4D28439DBC5DCD4BC9A3DDA52F549E10375529115ED1EA9B82` | ELF64 AArch64, 727,655 bytes | all five |
| [`9/EH/.../arm64-v8a/libstlport_shared.so`](https://android.googlesource.com/platform/prebuilts/ndk/+/2f308b8bad568d044288b2e79fcc1a894fd58787/9/sources/cxx-stl/EH/stlport/libs/arm64-v8a/libstlport_shared.so) | `858B9C2C9719C83D2FA83C43C1294AB3EE0D399A2895727D5C887CEF34EE9BEA` | ELF64 AArch64, 926,160 bytes | all five |

For both, `llvm-readelf --dyn-syms --wide` reports the exact imports needed by
the Samsung libraries. `_ZSt4cout` is a 152-byte AArch64 object in both. This
confirms the mangling and a real AArch64 stream-object definition from the
historical source family.

It does **not** make these NDK blobs the preferred payload:

- SONAME is `libstlport_shared.so`, not `libstlport.so`;
- dependencies are `libc.so`, `libm.so`, and `libdl.so`, rather than the local
  Samsung platform runtime's `libc.so`, `libm.so`, and `libstdc++.so`;
- the EH variant embeds C++ ABI/unwind entries such as `__cxa_throw`,
  `__gxx_personality_v0`, and `_Unwind_Resume`;
- historical NDK documentation explicitly explains that
  `libstlport_shared.so` was named differently to avoid collision with
  system-level `libstlport.so`, which was not ABI-stable. See the official
  [NDK STLport change/documentation](https://android.googlesource.com/platform/ndk/+/26f2392%5E%21/).

Mixing/renaming it risks duplicate or interposed C++ runtime state, especially
around global iostream objects. It is an excellent ABI oracle and possible
disposable loader experiment, not yet a shippable dependency.

## 5. Reproducible build strategy (recommended)

Use a Linux case-sensitive filesystem and the original AOSP build, not the
current NDK r27 toolchain:

```sh
mkdir aosp-5.1.1 && cd aosp-5.1.1
repo init -u https://android.googlesource.com/platform/manifest \
  -b android-5.1.1_r1
repo sync -c
source build/envsetup.sh
lunch aosp_arm64-eng
make -j"$(nproc)" libstlport
```

The expected primary output is under
`out/target/product/generic_arm64/system/lib64/libstlport.so` (the intermediates
also contain an unstripped copy). Record the manifest commit set and SHA-256 of
the result. Do not alter the module name and do not substitute libc++.

Before any APK inclusion, require these static gates:

```sh
llvm-readelf -h -d --dyn-syms --wide libstlport.so
```

Expected:

1. ELF64, AArch64, shared object.
2. SONAME `libstlport.so`.
3. `DT_NEEDED` includes platform `libstdc++.so` and does not introduce a second
   application C++ STL.
4. All five exact dynamic exports exist, with `_ZSt4cout` typed as `OBJECT`.
5. No undefined non-public dependency beyond what the target/probe can resolve.

Then perform loader validation in a disposable 64-bit process on the target:

1. query `/system/lib64/libstdc++.so` availability and its `new/delete` plus
   `__cxa_atexit`/`__cxa_finalize` exports;
2. load the built platform `libstlport.so` by absolute app-native path;
3. `dlopen` each Samsung candidate with `RTLD_NOW`, capturing linker logcat;
4. only after clean loading, run JNI registration and one init/draw/deinit
   lifecycle with the exact Samsung dex classes;
5. package nothing until both effects survive repeated init/deinit and process
   restart.

## 6. Practical decision

Recommended order:

1. In parallel with the ripple port, produce the AOSP 5.1.1 platform ARM64
   runtime from source.
2. Use the target phone to verify platform `libstdc++.so` and run the disposable
   loader probe.
3. If a Samsung Note 5 AOJ4 `system/lib64/libstlport.so` is later obtained from
   a provenance-verifiable firmware image, compare its exports, dependencies,
   `.comment`/build metadata, and behavior against the AOSP build. Prefer the
   same-firmware Samsung binary when redistribution/provenance permits.
4. Keep the current hand-written shim probe-only. Its arbitrary `std::cout`
   storage and simplified failure/allocator behavior do not reproduce the
   historical ABI.

This route is materially stronger than a five-symbol shim: it restores the
full allocator pools, stream layout/initialization, locale/facet state, and
historical no-exception semantics expected by the vendor binaries.
